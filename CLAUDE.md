# Working on conflux

conflux is a personal inference mesh for Apple devices. Start with
[README.md](README.md), then [docs/design.md](docs/design.md),
[docs/clients.md](docs/clients.md) and [docs/plan.md](docs/plan.md).

## Building

A Swift package, macOS 14 or later, with no dependencies beyond the SDK:

```bash
swift build
```

```bash
swift test
```

Tests use Swift Testing. CI runs both on every pull request, plus the
public-repository checks in `tools/ci/`.

The Mac app is also an Xcode project, generated by XcodeGen from
`project.yml` and never committed. Generate it, and again after adding,
renaming or removing a file under `Sources/conflux`:

```bash
ci_scripts/ci_post_clone.sh
```

Then archive and check it the way CI does, signed ad hoc:

```bash
tools/ci/build-app.sh
```

The Release configuration treats Swift warnings as errors, because Xcode Cloud
builds Release. [docs/releasing.md](docs/releasing.md) covers the app, Xcode
Cloud and TestFlight.

## Pull requests

When the work was asked for, or follows a plan that was agreed, open the pull
request as soon as it's done and checked. Don't stop to ask whether to: the
pull request is where it gets reviewed, and the merge is the decision. Commit
on a branch, never on `main`, and say in the description what was tested and
what wasn't. Work nobody asked for still needs asking about first.

**The title is the commit message.** Pull requests are squash merged: the
title becomes the commit's subject and the description its body, and
release-please reads both to choose the next version and write the changelog.
So the title is a [Conventional Commit](https://www.conventionalcommits.org/),
`type(scope): description`, and the `commit message` check enforces it:

- `feat` for something new a user can do: a minor release while below 1.0.
- `fix` for something that was wrong, `perf` for something faster: a patch
  release.
- `docs`, `test`, `ci`, `build`, `refactor`, `style`, `chore`, `revert`: no
  release by themselves.
- `type!` for a breaking change, with a `BREAKING CHANGE:` line in the
  description saying what breaks.

The title is a changelog entry, so write it for someone reading release notes:
what changed, in plain words, without a trailing period. In the description,
don't start a line with something shaped like a title, such as `fix: …`:
release-please reads it as another change.

## This repository is public

Everything here is public: files, commit messages, branch names, pull requests,
issues, review comments, CI logs and release notes. Write everything for that
audience.

### Clients are generic

conflux is a standalone tool. **Don't name or describe any specific application
that uses it**, and don't refer to private repositories, their issues or their
code. Write about "clients" and "client requirements." When a client's needs
shape a decision, state the need in general terms: "clients often treat
repeated timeouts as a dead server," not what a particular app does. This
applies even when the information is accurate and harmless.

Don't copy code from private repositories. Reimplement the pattern.

### No secrets

- No keys, tokens, passwords, certificates or provisioning profiles.
- No Apple Developer Team ID in tracked files. It goes in
  `App/Signing.local.xcconfig`, which is ignored, and on Xcode Cloud
  `ci_scripts/ci_post_clone.sh` writes that file from `CI_TEAM_ID`. Write
  examples as `<team ID>`.
- No App Store Connect API keys, export options or committed Xcode projects.
  Xcode writes the team into a project, so `conflux.xcodeproj` stays
  generated.
- No iroh secret keys, and no endpoint IDs of real devices, in code, tests,
  logs or docs. Tests generate their own.

### No personal data

- **Test images are generated, or openly licensed** (CC0 or similar), with
  EXIF and other metadata, GPS especially, stripped before committing. Never
  personal photographs.
- Benchmark results are committed only as scrubbed summaries: device class and
  chip, not hostnames, serial numbers, IP addresses, Apple Account details or
  endpoint IDs. Raw output goes in `tools/bench/results/`, which is ignored.
- Logs and screenshots in issues and pull requests get the same scrubbing.

### No model weights

Weights are fetched, never committed. Document where a model comes from and
under what license. Some model licenses restrict redistribution or use, so
conflux points at models and doesn't ship them.

### Dependencies

Pin binary dependencies by version **and** checksum, the way
[apple-iroh](https://github.com/misterbisson/apple-iroh) releases are consumed.
A tag can be moved, a checksum can't.

apple-iroh is maintained alongside conflux, and other apps depend on it.
Changes to it must be additive, keep existing defaults, and be useful beyond
conflux.

## CI

The repository is public so GitHub's macOS runners are free. That also means
anyone can open a pull request that runs workflows. So:

- **Pin third-party actions by full commit SHA**, with the version in a
  comment, never by tag.
- Set **`permissions: contents: read`** at the top of every workflow, and grant
  more per job only where needed.
- **Never use `pull_request_target`** to build or run code from a pull
  request.
- **No secrets in workflows that pull requests can trigger.** GitHub signs
  nothing: Xcode Cloud signs and uploads releases, so no signing secret
  belongs in GitHub at all.
- **No self-hosted runners.** On a public repository they run strangers' code
  on our machines.
- Keep the repository setting that requires approval before workflows run for
  first-time contributors.
- Workflow permissions default to **read**, with **Allow GitHub Actions to
  create and approve pull requests** on, so release-please can open its
  pull request. No workflow approves pull requests.
- **Xcode Cloud builds `v*` tags only.** Never give it a pull request or
  branch start condition: a pull request build runs the pull request's
  `ci_scripts/` where the team's signing is set up. No environment variables
  or secrets in its workflows, and its GitHub access covers this repository
  only.
- **`ci_scripts/` print no environment**: no `set -x`, `env` or `printenv`,
  and never the Team ID.
- **Xcode Cloud uses its latest Xcode, unpinned.** `.xcode-version` records
  which one that is, and GitHub's macOS jobs use it. Change it when Xcode Cloud
  moves; a weekly workflow opens an issue when it's behind.
- `tools/ci/check-public.sh` enforces what it can of this file: no weights or
  large files, no image metadata, pinned actions, no `pull_request_target`, no
  self-hosted runners, no secrets or signing in workflows, no Team ID,
  provisioning profile setting, key, certificate, profile, export options or
  Xcode project in the repository, and executable `ci_scripts/` that don't
  print the environment. Run it before pushing. When a rule here changes,
  change the check with it.
